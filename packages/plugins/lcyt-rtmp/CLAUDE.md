# `packages/plugins/lcyt-rtmp` — RTMP Relay Plugin (v0.1.0)

RTMP relay, HLS streaming, audio-only radio, stream preview, caption injection, and server-side speech-to-text transcription. Extracted from `lcyt-backend` into its own plugin for modularity. Imported by `lcyt-backend` as `lcyt-rtmp`.

**Main entry:** `src/api.js`
**Usage in lcyt-backend:**
```js
import { initRtmpControl, createRtmpRouters } from 'lcyt-rtmp';

const rtmp = await initRtmpControl(db, store);
const { relayManager, hlsManager, radioManager, previewManager, hlsSubsManager, sttManager } = rtmp;

// Wire hlsSubsManager into the video route for subtitle sidecar support:
setHlsSubsManager(rtmp.hlsSubsManager);

if (process.env.RTMP_RELAY_ACTIVE === '1') {
  // `auth` here should be scopedAuth('rtmp')/createProjectAccessMiddleware,
  // not the plain session-only middleware — only the four config-shaped
  // sub-routers below (ingestion/stream/radio's /config pair/crop) consume
  // it at all; the public/callback ones never take an auth param. opts.requireSetup
  // (plan_project_roles.md) gates their writes at Setup tier; defaults to a
  // no-op passthrough when omitted.
  const routers = createRtmpRouters(db, scopedAuth('rtmp'), rtmp, { allowedRtmpDomains, requireSetup: requireProjectRole(db, 'setup') });
  app.use('/rtmp',       routers.rtmpRouter);
  app.use('/feed-rtmp',  routers.feedRtmpRouter);
  app.use('/ingestion',  routers.ingestionRouter);
  app.use('/stream',     routers.streamRouter);
  app.use('/stream-hls', routers.streamHlsRouter);
  app.use('/radio',      routers.radioRouter);
  app.use('/preview',    routers.previewRouter);
}

// In graceful shutdown:
await rtmp.stop();
```

**Source files (`src/`):**
- `ownership.js` — `withOwnership(manager, spec)` Proxy used in shared mode (lcyt-backend `cluster/ownership.js`): claiming calls (`start`) take the lease `proc:<kind>:<key>`, routed calls (`stop`, `applyPosition`, ...) go to the holder, marks are passed on best effort, reads via `readThrough()`/`__read`; `__invokeLocal` is the whitelisted entry for forwarded calls. Method lists: `RELAY_OWNERSHIP`, `CROP_OWNERSHIP`, `STT_OWNERSHIP`. `initRtmpControl` wraps only when given `ownership`.
- `api.js` — `initRtmpControl(db, store?)` + `createRtmpRouters(db, auth, managers, opts)`. Returns all manager instances and a `stop()` function.
- `rtmp-manager.js` — `RtmpRelayManager`: manages RTMP relay sessions; calls `probeFfmpeg()` on startup. Fires `onStreamStarted`/`onStreamEnded` callbacks for DB stat tracking. Server-side DSK RTMP composite (`setDskRtmpSource(apiKey, rtmpUrl, { chromaKey })`) optionally chroma-keys the overlay via the exported pure `buildDskCompositeFilter(chromaKey)` (`plan_dsk_viewport_settings` Phase 5) — no chromaKey = today's opaque full-frame overlay; the composite viewport's `stream.chromaKey` is passed in by `lcyt-dsk`'s `on_publish`. Named-feed publish tracking uses a separate `_feedPublishing` Set + `markFeedPublishing(cameraKey)`/`markFeedNotPublishing(cameraKey)`/`isFeedPublishing(cameraKey)`, kept apart from the apiKey-keyed `_publishing`/`markPublishing`/`isPublishing` so an operator-chosen `camera_key` string can never collide with (or spoof) a real project's live status. Multiple projects' camera-sourced relay slots referencing the same named feed are reconciled into one shared MediaMTX fan-out registration via `_reconcileCameraKeyFanout(cameraKey)` (rebuilds the path's `runOnPublish` tee from the union of every apiKey's slots for that `cameraKey`, only deleting the path once none remain) — this replaces an earlier last-writer-wins `addPath`/`deletePath` call that let two projects sharing a `camera_key` clobber each other's registration. `start()`'s per-`cameraKey` loop is isolated with its own try/catch so one malformed/unsafe camera-sourced group can't abort the program-sourced slots processed afterward (defense in depth — `CAMERA_KEY_RE` validation at camera create/update time in `lcyt-production` should already prevent an unsafe value from ever reaching here). Per-slot transcoding (Phase 7) re-encodes **every** program-sourced slot's video stream in one ffmpeg process once any single slot sets `scale`/`fps`/`videoBitrate`/`audioBitrate` (the `filter_complex split` means none of them can stream-copy) — `MAX_TRANSCODE_SLOTS` (8) is a hard technical ceiling on that mode alone (uncapped relay slot counts, see `db/relay.js` below, are fine for plain tee/copy fan-out; unbounded concurrent libx264 encodes in one process is a real resource-exhaustion risk).
- `fanout-supervisor.js` — `FanoutSupervisor`: the one place relay fan-outs (MediaMTX path -> relay targets, `ffmpeg -re -i rtsp://… -c copy -f tee`) are registered; `RtmpRelayManager` calls `set(path, spec)`/`clear(path)` at all five sites (plain relay `{key}`, processed `{key}-out`, per-slot `{key}-t{i}`, crop `{key}-crop`, named feeds). `mediamtx.fanout_mode`: `hook` (default) = MediaMTX `runOnPublish` as before; `runner` = the supervisor starts the same command through `createFfmpegRunner` (`FFMPEG_RUNNER=spawn|fleet`; `-rtsp_transport tcp`, job `class: 'stream'`, `requires` from `mediamtx.fleet_requires`, RTSP base `mediamtx.rtsp_fleet_base_url` for remote workers) while the path is ready, restarts with backoff, and uses a deterministic job id (path + targets + publish episode) so a second instance adopts a running fleet job. Triggered by `POST /internal/mediamtx/path` (`routes/mediamtx-hook.js`, `x-lcyt-hook-secret` = `mediamtx.hook_secret`, closed while unset; fed by MediaMTX `runOnReady`/`runOnNotReady`, see `docker/mediamtx.yml`) plus a reconcile poll (`mediamtx.fanout_poll_ms`, default 2 s without a hook secret, 30 s with one). Not yet: forwarding a hook that lands on a non-owner instance (the owner's poll catches it), orphan reaping after an owner crash, queue-timeout fallback to local. Tests: `test/fanout-supervisor.test.js`, `test/mediamtx-hook-route.test.js`; never run against a real MediaMTX or fleet.
- `crop-manager.js` — `CropManager`: starts/stops a per-key crop renderer, persists crop config and position state, and reuses the same ffmpeg runner abstraction as the relay manager.
- `crop-follow.js` — pure auto-follow geometry (`targetCenter`, `xNormForCenter`, `createFollowSmoother`), used by lcyt-backend's `crop-follow-controller.js`; `crop_config.auto_follow` (opt-in, `autoFollow` in `getCropConfig`/`setCropConfig`, checkbox on the crop settings dialog).
- `routes/crop.js` — `/crop/*` session-authenticated CRUD API for crop config, presets, preset sets, and live position updates. Writes require Setup-tier project role (`opts.requireSetup`, plan_project_roles.md) — reads stay open to any project member.
- `hls-manager.js` — `HlsManager`: tracks which streams have HLS enabled and serves their playlist info. The HLS itself is produced by MediaMTX: `start()` registers the path (`mediamtxClient.addPath`) and the public `/stream-hls` routes proxy MediaMTX's HLS output (`mediamtx.hls_base_url`). It runs no ffmpeg and writes no segment files (the old `localRtmp` ffmpeg re-mux and the storage-publishing watcher were never wired in production and were removed). `probeStreamInfo(hlsKey)` runs `ffprobe` against MediaMTX's internal HLS URL (60s cache, hard-coded fallback on failure) and builds the real `BANDWIDTH`/`CODECS` values consumed by `lcyt-backend/src/routes/video.js`'s `buildMasterManifest()`.
- `radio-manager.js` — `RadioManager`: dual-mode audio-only HLS. **ffmpeg mode** (default): spawns ffmpeg RTMP → AAC HLS. **mediamtx mode**: no ffmpeg; MediaMTX serves HLS, `NginxManager` writes slug-based nginx proxy locations.
- `nginx-manager.js` — `NginxManager`: writes nginx `location` blocks for MediaMTX radio streams. Atomic file write + `nginx -t && nginx -s reload`. No-op when `NGINX_RADIO_CONFIG_PATH` is unset.
- `preview-manager.js` — `PreviewManager`: manages MediaMTX API or ffmpeg for RTMP → JPEG thumbnail generation.
- `hls-subs-manager.js` — `HlsSubsManager`: rolling WebVTT segment writer for subtitle sidecars. Optional `store` (object store, passed as `hlsSubsStore` to `initRtmpControl` when `FILE_STORAGE=s3`) holds segments, `playlist.m3u8` and `meta.json` so any instance can serve them; routes use the async `readLanguages`/`readPlaylist`/`openSegment`.
- `mediamtx-client.js` — `MediaMtxClient`: REST API client for MediaMTX v3 (drop publisher, list streams, `addPath`/`patchPath`/`deletePath`; the relay manager uses add-then-patch upsert so reconfiguring a relay replaces a leftover path config instead of failing).
- `hls-segment-fetcher.js` — `HlsSegmentFetcher`: polls a MediaMTX fMP4 HLS playlist, detects new segments, emits `segment` events with `{ buffer, timestamp, duration, url, index }`. Used by `SttManager`.
- `stt-manager.js` — `SttManager` (`EventEmitter`): manages one STT session per API key. Wires `HlsSegmentFetcher` → STT adapter → transcript → `session._sendQueue` for delivery. Supports `hls`, `rtmp`, `whep` audio sources and the `auditor` provider (a transcript source that pulls the stream itself). **Events:** `transcript`, `error`, `stopped`. `setDeliveryHelpers({ getTranslationVendorConfig, getTranslationTargets, writeBackendCaptionFiles, composeCaptionText, fanOutToTargets })` injects the lcyt-backend helpers used by `_deliverTranscript`: Phase 5 server-side translation, backend caption-file archiving (`createSessionCaptionFileWriter`), default composition (`composeCaptionText`, using the captions-target row's `show_original` with the vendor-config flag as fallback), and extra-target delivery via the shared `createCaptionFanout` — same per-target routed composition and viewer-owner registration as `POST /api/v1/captions`. Without injected helpers, transcripts go only to the legacy primary sender (uncomposed).
- `stt-adapters/google-stt.js` — `GoogleSttAdapter`: posts fMP4 segments to Google Cloud Speech-to-Text REST API or streams via gRPC (`GOOGLE_STT_MODE=grpc`). Emits `normalisePunctuation`-cleaned transcripts.
- `stt-adapters/auditor-live.js` — `AuditorLiveAdapter`: pull-type transcript source (provider `auditor`, not an audio source: no audio passes through LCYT and `audioSource` is reported as `none`). Sends no audio: `POST /api/v1/v1/live` asks the auditor STT service (liturgos-auditor-stt) to pull `AUDITOR_STT_SOURCE_URL` (rtsp/srt from MediaMTX, on an fffleet worker when the service runs `AUDITOR_STT_STRIP=fleet`), then reads `GET /api/v1/v1/live/:id/events` (SSE). Emits final `transcript`s only (`confidence: null`, `timestamp` = the segment's absolute `wall_start`). A session that ended (service restart, stream lost) is replaced with backoff; a dropped connection resumes with `Last-Event-ID`. `hls`/`rtmp`/`whep` and the other adapters are unchanged. Tests: `test/auditor-live.test.js` (fake service). Never run against a real service, MediaMTX or fleet.
- `stt-adapters/whisper-http.js` — `WhisperHttpAdapter`: sends audio to a Whisper-compatible HTTP STT server.
- `stt-adapters/openai.js` — `OpenAiAdapter`: sends audio to OpenAI-compatible STT endpoint.
- `stt-adapters/pcm-buffer.js` — `PcmSilenceBuffer`: accumulates PCM frames and detects silence; `buildWav()` helper constructs WAV from raw PCM bytes.

## Server-side STT Architecture

Server-side speech-to-text transcription converts an incoming RTMP/HLS/WHEP audio stream into captions without requiring a browser microphone. Transcripts are injected directly into the session's `_sendQueue` and delivered to YouTube just like manually typed captions.

**Audio sources:**
| Source | How it works |
|---|---|
| `hls` | `HlsSegmentFetcher` polls MediaMTX fMP4 HLS playlist (`MEDIAMTX_HLS_BASE_URL`, default `http://127.0.0.1:8080`); segments sent to STT adapter |
| `rtmp` | ffmpeg reads RTMP stream and writes PCM/WAV frames to the adapter's stdin |
| `whep` | ffmpeg reads WHEP (WebRTC-HTTP Egress Protocol) stream from MediaMTX's WebRTC port (`MEDIAMTX_WEBRTC_BASE_URL`, default `http://127.0.0.1:8889`) and writes PCM frames |

**Providers:**
| Provider | Class | Notes |
|---|---|---|
| `google` | `GoogleSttAdapter` | REST (default) or gRPC (`GOOGLE_STT_MODE=grpc`); service account or API key auth |
| `whisper_http` | `WhisperHttpAdapter` | Any Whisper-compatible HTTP endpoint |
| `openai` | `OpenAiAdapter` | OpenAI `/audio/transcriptions`-compatible endpoint |

**Confidence filtering:** Each `POST /api/v1/stt/start` request accepts an optional `confidenceThreshold` (0–1). Transcripts below the threshold are silently dropped.

**Per-key config persistence:** `GET/PUT /stt/config` stores preferred provider, language, audioSource, and confidenceThreshold in the DB (`getSttConfig`/`setSttConfig` in this plugin).

The HTTP routes for STT (`/stt/*`) live in `packages/lcyt-backend/src/routes/stt.js` and delegate to `SttManager` here — see `packages/lcyt-backend/CLAUDE.md`.

## Crop per output (plan_egress_outputs.md PR 2)
`/crop/*` accepts `outputId` (query or body). A **crop scope** is `{ apiKey, outputId, isDefault }` (`resolveCropScope`, `listCropScopes`, `src/db/crop.js`): the default crop (`crop_config`, session key = api key, path `{apiKey}-crop`) is unchanged for every old caller; another output's crop lives in `output_crop_config` with session key = output id and path `out-<id>-crop`. `src/crop-outputs.js` computes source/output paths (`cropSpec`), refuses a crop on an already cropped output (`checkCropChain`, until the PR 3 step supervisor) and starts/stops the crops hanging on a feed (`startCropsForFeed`/`stopCropsForFeed`, called from `routes/rtmp.js` for the main stream and `routes/feed-rtmp.js` for named feeds). `CropManager.start(key, config, { sourcePath, outputPath, apiKey })`; `applyForSource` iterates all scopes. `routes/outputs.js`: `GET/POST/PATCH/DELETE /outputs` (Setup tier writes). Never run against a real MediaMTX.

## DSK step per output (plan_egress_outputs.md PR 3)
`src/output-steps.js`: an output whose `dsk` list has viewports gets one ffmpeg (`buildDskStepArgs`) that reads its source path, composites each viewport's own stream (`dsk/<apiKey>__<viewport>`, chroma-keyed per the viewport's `stream.chromaKey`, scaled to the picture with `scale2ref`) and publishes `out-<id>-dsk` (RTMP into MediaMTX, like the crop). `OutputStepManager` supervises these runs like `FanoutSupervisor`: runner factory (`FFMPEG_RUNNER`), restart with backoff, a poll (`outputs.step_poll_ms`, default 3 s) plus a kick from the `/outputs` routes; a step runs only while its source path is ready, with the viewports ready at that moment, and restarts when that set changes. `outputs.max_steps` (`MAX_OUTPUT_STEPS`, default 4) caps DSK steps plus crops per project; `outputs.steps_active` (`OUTPUT_STEPS_ACTIVE`) switches the layer off. `GET /outputs/steps` shows running and skipped steps. `src/output-paths.js` holds the path rules: an output reads its feed or the final picture of the output it is built on (crop, else DSK step, else that output's input), so a crop of such an output reads `out-<id>-dsk`. Composite-mode viewports were skipped by the step at first (the relay composited them); they are included now, see "Legacy composite DSK moved" below. Not yet: multi-instance ownership of steps (every instance would try; MediaMTX refuses the second publisher), relay slots reading `out-<id>-dsk`. Started from `server.js` after the outputs backfill when the relay stack is active. Never run against a real MediaMTX or fleet.

## Relay slots from outputs and audio replace (plan_egress_outputs.md PR 4)
`POST/PUT /stream` accepts `sourceOutputId` (an `outputs.id` of the project; 400 if unknown or sent with `sourceFeedId`). `src/output-routing.js` `resolveOutputRoute()` decides what the slot sends: the output's final picture (crop, else DSK step, else what it reads). `getRelays` applies it: **`program`** (the main stream without a step) and **`crop`** (the default crop `{apiKey}-crop`) leave the slot on the old program/crop handling (CEA-708, transcoding, the relay's own DSK composite still work; an old 'crop' slot never turns into a program slot because its crop is off); any other route becomes a feed-style slot (`sourceFeedKey` = the path: a named feed, `out-<id>-dsk`, `out-<id>-crop`) fanned out by the existing per-path `FanoutSupervisor` registration. `outputs.audio_source` `{feed:id}` adds `sourceAudioPath` (the audio feed's path; `media` must not be `video`): such slots form their own group `<video path>|a|<audio path>` and ffmpeg maps video of the first and audio of the second input, both copied (`FanoutSpec.audioPath`); the fan-out waits until both paths are ready. **Audio replace needs `mediamtx.fanout_mode=runner`** (a hook-mode registration is bound to one path; there the slot keeps its own audio and a warning is logged). No sync offset (the audio feed can drift). `routes/feed-rtmp.js` also starts the owner's relay when a feed publishes and the project has output slots. Not yet: multi-instance ownership of steps (the legacy composite moved into Program's step, see "Legacy composite DSK moved" below). Never run against a real MediaMTX or fleet.

## Legacy composite DSK moved into the program output's step (plan_egress_outputs.md follow-up)
The composite DSK viewport (`display_settings.stream.mode === 'composite'`, the one overlay on the program picture, stream `dsk/<apiKey>`) is now keyed by the DSK step of the output that lists it (Program after the backfill) instead of the relay's own ffmpeg. `effectiveDskViewports` includes it (`composite: true`, bare path `dsk/<apiKey>`, chromaKey from its stream) while `outputs.composite_in_step` (env `OUTPUT_COMPOSITE_IN_STEP`, default on) is set; off = the old behaviour (steps skip it, the relay composites). `compositeHandledBySteps(db, apiKey)` (`output-paths.js`; needs `outputs.steps_active` too) is the gate `RtmpRelayManager.setDskRtmpSource` asks (`setCompositeGate`, wired in `initRtmpControl`): when a step keys the stream the relay keeps no composite state, so nothing is keyed twice. Path helpers read the same settings through `setOutputSettings()`. Slots: a plain 'program' slot (no feed, no output) and a slot on the program output read `out-<id>-dsk` while a step keys the composite (`getRelays` maps them, `programOutputId`); slots needing the relay's own ffmpeg (CEA-708, scale/fps/bitrate) keep the raw program, as before (the old composite never applied to them). `resolveOutputRoute` marks such routes `programStep: true`; with `outputs.steps_active` off no route points at a step path. **Cost:** the step re-encodes the program (libx264 veryfast) all the time while the composite viewport is in an output's DSK list, not only while DSK graphics are published, and program slots read that re-encoded picture. Never run against a real MediaMTX or fleet. Tests: `test/output-routing.test.js` ("composite DSK viewport moved..."), `test/output-steps.test.js`.
